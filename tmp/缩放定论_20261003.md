# 缩放定论（10/03，源码验证）：原版玩家渲染 = 0.9375 缩放

> 取代 `UV原理_模型对比_20261001.md` §8 中"两管线等大"的结论——那条链把
> `LivingEntityRenderer.render:102` 处的 `S(entityScale)` 记为 1.0，漏了
> `PlayerRenderer.scale()` 的 0.9375 覆写。

## 1. 源码定案

`transformed\net\minecraft\client\renderer\entity\player\PlayerRenderer.java`
（两个反编译 hash 目录交叉验证一致）：

- L159–162 `scale(PoseStack, LivingEntity, float)`:
  `posestack.scale(0.9375F, 0.9375F, 0.9375F)`
- `LivingEntityRenderer.render:102` 调用它。调用链顺序（render L97–103）：
  `S(entityScale=1.0)` → `R(yaw)` → `S(-1,-1,1)` → **`S(0.9375)`** → `T(0,-1.501,0)`

⇒ 原版玩家最终渲染 = 32px 模型 × 0.9375 = **30px = 1.875 块**（脚踩地，头顶 1.875；
略高于 1.8 碰撞盒——这正是玩家头能顶过 1 格缝隙的原因）。

Spark 管线（ModelModule/BonePose/OCube）无此缩放 ⇒ 未缩放的 Spark 玩家模型 = 2.0 块
= 比原版大 6.67% = 用户长期看到的"更大"。用户研究一致："基岩版模型需要缩放，
Spark 正是基岩版；Java 版不需要（自带 0.9375）"。

旧 MODEL_SCALE 0.9454（=537/568 屏幕量测）方向对、数值错；真值 0.9375 是源码值。

# 10/05 修订（最终定案，取代 §2/§3 的几何烘焙方案）

## 8. 10/03 方案的回归与根因

用户 10/05 实测：尺寸 ✓（"高度没问题了"），但贴图回归——**"皮肤整体被缩放，只保留左上角"**。

**根因（源码验证，`OPolygon.of()` box-UV 分支，`tools\_spark_core_src\...\origin\OPolygon.kt:60`）**：
box-UV 的 UV 矩形 = `cube.size.scale(16.0).toVector3f().floor()`（从 cube 三维尺寸推导，
锚在同一 uv offset）。OModel 数值在 ModelModule 解析期已 ÷16（块单位），1:1 身体 cube
（如 4×12×4 px）×0.9375 → 3.75×11.25×3.75 块 → ×16 = 60×180×60 → **floor = 59×179×59**
⇒ UV 矩形比贴图采样区小一圈且锚点不变 ⇒ 采样区相对模型放大 = "整体缩放、只留左上角"。
剑 cube 走 face-UV（显式 uv+uv_size）不受影响 ⇒ 症状只在身体。
**结论：任何 Spark 玩家模型的几何缩放都会破坏 box-UV——几何烘焙方案作废。**

## 9. 10/05 落地方式：1:1 几何 + root 骨运行时缩放钳制

- 模型回原版 1:1（`gen_wrist_player_sword_v3.js` 的 `VANILLA_RENDER_SCALE=1.0`，
  scaleBoneInPlace 保留为无害 no-op）；3 个实体动画全部回 1:1 关键帧
  （两个生成器 S=1.0；`scale_entity_anim_positions.js` 作废，不再运行）。
- **0.9375 改为运行时施加**：`SwordPlayerModelHandler.onBoneUpdate(BoneUpdateEvent)`
  对 `(entity, catoxidesbattlerebuild:player_wrist)` 模型的 **root 骨**把 scale 分量钉在
  (0.9375,0.9375,0.9375)，每 tick 生效（只替换 scale；root 的动画 pos/rot 保留）。
  root pivot=(0,0,0) ⇒ 绕脚等比缩放全部子骨含动画位移 = 原版 poseStack.scale 语义。
- **事件链（源码闭环）**：物理线程 `AnimApplier.physTick → AnimController.physTick →
  bonePose.updateInternal(blendBone(bone))`（未提及的骨重置 scale=1）→ 主线程
  `AnimController.tick → bonePose.setChanged()` → `NeoForge.EVENT_BUS.post(BoneUpdateEvent)`
  → 全部监听器（含 Spark 自家 BoneModifier、我们的钳制）→ `localTransform = event.newTransform`。
  我们的 listener 是 `@EventBusSubscriber(bus = Bus.GAME)` = NeoForge.EVENT_BUS ✓ 同总线。
- 钳制对所有动画自动生效（每 tick 重算后钳）；基线 (entity, minecraft:player) 无钳制
  = 2.000（Spark 参考值，非原版渲染值）。
- 与 Spark 自家 `BoneModifier`（`animation/vanilla/BoneModifier.kt`）同机制共存：
  它对 "head" 骨加 (−player.xRot, −yHeadRot+yBodyRot, 0)、对 "root" 骨处理睡觉偏移
  （读 `originNewTransform`，睡觉时会覆盖我们钳制的 scale——仅睡觉瞬间，可忽略；
  若将来要共存需读 `newTransform` 而非 origin）。

## 11. 顺带定案：JOML rotateZYX 约定（4 个离线工具曾是错的）

`Quaternionf.rotateZYX(Vector3f)` = `rotateZYX(v.z, v.y, v.x)` = **Rz(iz)·Ry(iy)·Rx(ix)**
（JOML 1.10.5 源码+字节码+Java 探针三重验证；Spark 自家 `AnimController.blendBone:68`
显式 `rotateZYX(rot.z, rot.y, rot.x)` 同约定）。`matToEul`（sy=−m[2][0]）是其精确逆
⇒ **游戏内姿态一直是 IK 目标值**；错的只是 4 个离线仿真工具
（verify_pose_v3 / check_scale_pose / gen_wrist_sword_anim_v3 / search_embedding_v3
的 rotZYX 用成了 Rx·Ry·Rz）——已全部修正。生成器自检腕落点 Δ：1.937px → 0.001px（舍入）。
文件↔内部旋转换算不变：内部 = (−fileX, −fileY, +fileZ) 弧度。
